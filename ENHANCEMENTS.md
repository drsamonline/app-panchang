# Enhancements

What is worth doing next, ordered by what it buys the reader. Every item here is
achievable **offline, with no internet and no external dependency** — no API, no CDN, no
webfont, no package that fetches anything at runtime. Where an item would need the network,
it is not on this list; the "not doing" section at the end says so explicitly.

Effort: **S** under an hour · **M** an afternoon · **L** a day or more.

---

## 0. Shipped in this pass

For honesty about the starting point, these are done and are no longer open items:

- the landing page, its own design, with the real app embedded and driven by guided buttons;
- local SVG badges, generated by `scripts/badges.py`, and screenshots by `scripts/shot.py`;
- **a bug that made the app render an empty day**: the astronomy was split out of
  `panchang.js` into a kit that was never added to the page's script tags, so the engine
  threw on load. The estate's kit guard forbids retrofitting a kit into an existing page,
  so the core is inline in `panchang.js` and the page loads only its own scripts. A test
  reads the page and fails if either the wiring or the self-containment breaks;
- deep links — `#d=…&lat=…&lng=…&tz=…&lang=…&muhurat=1` — so a day can be linked or shared;
- a service worker (HTML network-first, assets cache-first, cache bumped per release) and a

- a build stamp in the app footer, so "am I on the new one?" is answerable from the page;
- 13 new assertions: page wiring, an offline guard, and the offline shell's file list (24 → 37);
- the licence header in `panchang.js` said MIT while every other place said PolyForm
  Noncommercial 1.0.0.

## 1. Accuracy — the thing that matters most

**1.1 Tithi, nakshatra and yoga *end times*. (M)**
The app reports one set of limbs for local noon. A printed panchang reports when each limb
begins and ends, and that is what people actually use to pick a time. The elongation is a
smooth function of time, so the boundary is a root of `elongation(t) − 12k`; a bisection over
a twelve-hour window converges to under a second in about twenty iterations. Pure arithmetic,
no data, no network. This single change moves the app from "which tithi is today" to
"what time does the tithi change", and it makes the muhurat finder meaningfully better.

**1.2 Time-zone handling that is not a fixed offset. (S)**
The app takes a UTC offset in hours. For India that is always 5.5 and correct; for anywhere
with daylight saving, or for a historic date, it is wrong by an hour and the sunrise is
wrong with it. `Intl.DateTimeFormat` with a `timeZone` and `timeZoneName: "shortOffset"` is
built into every browser and gives the real offset for that date — no library, no data file.
Keep the manual offset as an override, add a zone picker.

**1.3 A proper Lahiri ayanamsa. (S)**
`ayanamsa()` is a linear approximation. The real value is a polynomial in time; replacing it
costs a few lines and tightens the sidereal positions, which is what nakshatra and yoga rest
on. Worth doing before 1.1, since boundary times inherit the error.

**1.4 The full lunar series. (M)**
The moon uses a reduced Meeus ch. 47 series. The full table takes longitude from about
0.05° to about 0.01°, which is the difference between a boundary being a minute out and a
few seconds out. It is a fixed table of coefficients in the source — no data file, no
dependency. Also add ΔT so the code is honest about the difference between TT and UT.

**1.5 Altitude and horizon. (S)**
Sunrise currently assumes sea level. An altitude input (and the standard −0.833° refraction
and semidiameter) fixes the sunrise for anywhere in the hills, and the app is used in India
where that is not a rounding error.

**1.6 Sunrise-to-sunrise as the day boundary, as an option. (M)**
Tradition differs: some panchangs run the day from sunrise, others from midnight. Offer it as
a setting rather than picking for the reader, and label which one produced the output.

## 2. More of the almanac, from the same arithmetic

All of these are computed from sunrise, sunset and the weekday — no data, no network.

**2.1 Choghadiya, hora, gulika-kaal and yamaganda. (S each)**
The day divided into eight, into planetary hours, and the two other inauspicious windows
beside Rahu Kaal. The tables are constants already sitting next to `RAHU_PART`; the pattern is
identical to what is there. Together these are the most requested additions.

**2.2 Abhijit and durmuhurtam. (S)**
Abhijit is the eighth of the daylight day, and the midday window people ask for by name.

**2.3 Masa, samvat, samvatsara, ritu and ayana. (S)**
The lunar month name, Vikram Samvat and Shaka Samvat years, the sixty-year samvatsara cycle,
the season and the solar half-year. All derived from the sun's sidereal longitude and the
new-moon count; they make the header read like a panchang instead of a table.

**2.4 Moon rashi, moonrise and moonset. (S)**
The moon's sign is one line from the longitude already computed. Moonrise and moonset are the
same sunrise equation with the moon's coordinates and a slower rate of change — the existing
`sunriseSunset` generalises.

**2.5 Bhadra. (S)**
Vishti karana is already computed; flagging it by name is the missing half.

**2.6 A festival table as rules, not dates. (M)**
About forty observances — the named Ekadashis, the Purnima and Amavasya names, Janmashtami,
Raksha Bandhan, Navratri, Shivratri, Ganesh Chaturthi — expressed as `{masa, paksha, tithi,
nakshatra}` rules in a bundled JSON file and resolved by the engine for any year. A list of
hard-coded dates goes stale; a rule table does not, and it stays correct for 2050.

**2.7 A rough eclipse flag. (L)**
New and full moon instants come from 1.1; proximity to a lunar node is a further calculation
on the same longitudes. "A lunar eclipse is possible tonight, check locally" is honest at
that precision. Do not attempt local visibility — that needs a horizon model and a lot of
testing to be worth shipping.

## 3. Place without typing coordinates

**3.1 A bundled city list. (M)**
Typing 19.0760 and 72.8777 is the worst part of the app. Ship a JSON of a few hundred Indian
cities with coordinates and offsets, searchable by name in the three languages. It is a data
file in the repository — no geocoding service, which is the point.

**3.2 Nearest city from the device's own GPS. (S)**
Geolocation is already used and is not a network call. Offline reverse geocoding is not
possible without a big dataset, but "the nearest city in the bundled list" is, and it gives
the place a *name*, which is what the reader wants.

**3.3 Remember more than one place. (S)**
The app stores one place. A short list with labels ("home", "clinic") is a few lines on top
of the existing storage.

## 4. Install, print, and get data out

**4.1 An install prompt. (S)**
The manifest and service worker are in place. A small "install this" affordance when
`beforeinstallprompt` fires turns a bookmark into an app on Android, with no store.

**4.2 A print stylesheet. (S)**
One page for the day, one for the month: black on white, no controls, no frame. People pin
these up. It is a `@media print` block, nothing more.

**4.3 Calendar export (`.ics`). (S)**
Muhurats, observances and Rahu Kaal windows as an iCalendar file the phone's own calendar
imports. Generated in the browser, downloaded, never uploaded — the same shape as the CSV
export that already exists.

**4.4 JSON export and import. (S)**
So a place list, a set of saved days and the settings survive a reinstall without a server.
The CSV is for spreadsheets; this is for the app.

**4.5 A computed-year cache. (S)**
A year of panchang is 365 × a few hundred floating-point operations. Precompute it into
IndexedDB once and month navigation becomes instant on a cheap phone.

## 5. Languages and accessibility

**5.1 Translate the *values*, not just the labels. (M)**
This is the real gap. The headings become तिथि and નક્ષત્ર, but the tithi is still "Krishna
Saptami" and the nakshatra is still "Pushya". The three name tables — 30 tithis, 27
nakshatras, 27 yogas, 11 karanas, 7 vaaras — need Devanagari and Gujarati forms, plus the
lunar month names from 2.3.

**5.2 Native numerals. (S)**
An option for ०१२३ / ૦૧૨૩ in times and dates, off by default, remembered like the theme.

**5.3 High-contrast and larger text. (S)**
The theme system already carries variables; a third theme and a root font scale are cheap,
and the audience for a panchang skews older.

**5.4 Keyboard and screen-reader pass. (S)**
The dial on the landing page is decorative; the app's cards are readable but unlabelled as a
group. Add landmarks, a table view of the day for screen readers, and a live region on the
muhurat results.

## 6. Releases with icons

The ask, spelled out. The goal is that a release is identifiable at a glance and its assets
are verifiable without trusting anyone.

**6.1 One icon source of truth, generated. (S)**
`docs/play/icon.svg` is the master. A `scripts/icons.py` should render every size from it —
192, 512, maskable 512, a Windows `.ico`, an Android adaptive foreground and background, and
a monochrome layer for themed icons — so no hand-made PNG can drift from the master. Half of
this exists now (192, 512, maskable); the `.ico` and the adaptive layers do not.

**6.2 The icon in every release body. (S)**
Release notes open with the icon, then the promise in one line, then the assets. GitHub
renders a release asset referenced by its own download URL, so the icon travels with the
release instead of being hot-linked from a branch that will move.

**6.3 Icons attached as release assets. (S)**
`icon-512.png` and `icon.svg` uploaded alongside the binaries, so a downloader can put a face
on the shortcut they make.

**6.4 A `SHA256SUMS` file per release. (S)**
Three lines and a `sha256sum -c` instruction. It costs nothing, it lets a cautious person
verify an unsigned Windows binary, and it makes the build's reproducibility a thing you can
check rather than claim.

**6.5 A versioned release per changelog entry, alongside the rolling build. (S)**
`app-latest` is the build; `v0.1.2` is the release with the changelog body. Both point at the
same commit, so the demo and the binaries cannot disagree. This pass does the first one.

**6.6 Confirm the binaries carry the icon. (S)**
The EXE and the APK are built by the shared `app-builder` kit. Check that the Windows
resource icon and the APK's `mipmap` come from this repo's icon rather than a placeholder; if
they do not, the fix belongs in `app-builder` so every app gets it at once.

## 7. Guardrails that keep the promise

**7.1 The offline scan. (done)**
`test-node.js` reads every shipped file and fails if a script, link or fetch points at
another origin. It is the only thing that will stop a future commit from quietly adding a CDN.

**7.2 A real offline render test. (S)**
`test-node.js` proves nothing is *loaded* from elsewhere; it does not prove the app *works*
without a connection. Chromium can be run with `--host-resolver-rules="MAP * ~NOTFOUND"` and
`--dump-dom`, and the DOM then checked for a rendered tithi. Zero dependencies, and it tests
the claim end to end.

**7.3 Badge claims read from the suite. (S)**
`scripts/badges.py` currently hard-codes "37 passing". Have it parse the suite's last line so
the badge cannot claim a number the tests do not print.

**7.4 A licence-agreement check. (S)**
The drift fixed in this pass — MIT in one header, PolyForm everywhere else — is exactly what
a one-line CI check catches: grep every source header, the README, the LICENSE and the
workflow's SPDX line, and fail if they disagree.

## 8. Tests worth adding

- **Boundary instants**: find where the elongation crosses each multiple of 12° over a year
  and assert the reported tithi changes exactly there.
- **Polar latitudes**: `sunrise` is null above the circle. The app must say so, not crash —
  and today nothing tests it.
- **A thousand-day sweep**: every index in range, every day, in one pass.
- **Southern hemisphere and negative offsets**: Sydney, Johannesburg, and a date either side
  of a DST change.
- **Golden file**: one printed panchang for three cities, transcribed into a fixture, so a
  change in the engine that moves a time by more than two minutes fails loudly.
- **The month export**: row count, column set, and a spot-checked row.

## 9. Not doing, on purpose

- **Any network call, ever** — no ephemeris API, no geocoding service, no update check.
- **Accounts, sync or cloud backup.** A panchang for a place is derivable; there is nothing
  worth holding on a server.
- **Webfonts.** The type is the system face, which is also why the page renders the same on a
  village phone as on a workstation.
- **Analytics of any kind.** Not even a hit counter.
- **Ads or sponsorship.** The licence is noncommercial and the app has no inventory.
- **A claim of exactness.** The accuracy note stays in the app, the README and the page.
